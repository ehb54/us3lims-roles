# How installs and upgrades are supposed to work (4.2.0 → 4.3.0 and beyond)

Written 2026-10-13 after round 14 of ehb54's review surfaced the same class of bug twice (the UTC migration, the ansible upgrade-invocation ordering) because the underlying model wasn't written down anywhere. Read this before touching `uslims_upgrade.php`, `migrations.php`, or any `us3lims-roles` task that calls either.

## The core distinction

There are three different actors, and keeping them separate is the whole point of this doc:

- **us3lims-roles** installs a brand-new LIMS *host* from scratch, or converges/upgrades a host that already exists.
- **newinst** creates one new *instance* (a dbinst checkout + its own database) on a host that is **already running**, whatever version that host happens to be on. This is not an install-time-only tool — a running 4.3.0 host uses newinst any time a new tenant needs a new instance, long after the host itself was installed or upgraded.
- **uslims_upgrade.php** transitions an *existing* host, and the instances that existed on it *before the transition started*, from 4.2.0 shape to 4.3.0 shape.

From those three actors, there are exactly two situations an instance (or host) can be in, and they are not variations of each other:

1. **Nothing pre-existing to convert.** This covers both a fresh 4.3.0 host install, and any instance newinst creates — on a fresh host, or on an already-upgraded host, or at any point afterward. `newinst`/`dbinst` write config in the current shape from the moment the instance is created, by construction, regardless of when that moment is. `people_audit` starts empty. **Nothing here should ever call the upgrade/migration machinery.** If it does, that's a bug in the install path, not a case the migration code needs to handle.
2. **An existing pre-4.3.0 host (and the instances that were already on it) being upgraded.** Its host config, its pre-existing instances' config, and their `people_audit` data are all in the *old* shape and need to move to the *new* shape exactly once. This is the only case `uslims_upgrade.php` exists for. An instance newinst creates on this same host *after* the pull is case 1, not case 2, even though it's running on the same, now-4.3.0, host.

Every bug this round traces back to blurring these two together — either by running the upgrade script unconditionally regardless of which case applies, or by trying to infer which case an *instance* is in from a signal (its own VERSION file) that newinst's normal, correct behavior (writing current-shape config at creation time) makes indistinguishable from "this instance existed before the pull and just got its checkout updated along with everything else."

## Why the upgrade script exists at all

It is not a general-purpose convergence mechanism. It exists because the *shape* of a 4.2.0 host and a 4.2.0 instance's data does not match what 4.3.0's code expects, and someone has to transform the one into the other. That transformation has three kinds of target:

- **Config/host-shape changes** — listen-config v2, `common_dir`, the circuit-breaker/ssh-control/elog directories, Content-Security-Policy. Scoped to the host, or to one instance's config file.
- **Data-shape changes** — `people_audit.created_at` moving from local time to UTC. Scoped to one instance's database.
- **Submission-architecture changes** — the reason the other two exist at all. 4.3.0 removes the Airavata/GFAC bridge entirely and replaces it with direct Slurm submission, hardened fault handling (the UNREACHABLE-vs-failure taxonomy, the circuit breaker, the remote_exec gateway), and a new metascheduler/pool layer for picking among clusters. Step 3 deactivates clusters the new Slurm code can't submit to (or converts national-HPC ones to SSH); step 5 creates the metascheduler's own tables (`gfac.metascheduler_decision`, `cluster_status_nudge`) where the account has privilege to; step 8 verifies every active cluster actually passes the new submission-sizing gate instead of refusing every job. A 4.2.0 host's whole cluster-submission model is gone in 4.3.0 — this is the real reason an existing host needs a deliberate, gated transition rather than just a config tweak.

All three kinds are one-time, all are idempotent (safe to rerun, a done step reports `ok` and changes nothing), and all are implemented as entries in dbutils' `migrations.php` registry or as steps in `uslims_upgrade.php` directly, run by the same script. That part of the design is correct and should be the pattern for the *next* shape change too, not just this one.

## The procedure, as `uslims_upgrade.php --help` actually documents it

This is manual and operator-driven, not an ansible convergence step:

1. Stop services (`php services.php stop` while the host is still on old code — post-upgrade, `systemctl stop us3-listen` instead, since the new code refuses a pre-upgrade config). Let queues drain. Comment out LIMS cron entries.
2. Pull code in two passes: `uslims_git_info.php --update-pull util` (dbutils itself), then `--update-pull lims` (common, gridctl, webinfo, dbinst base, **and every existing instance's own dbinst checkout**). Both passes are required — pulling `util` alone leaves the host in the exact stale-mix state step 0 is built to refuse.
3. Run `uslims_upgrade.php --check`, review, then `--apply`.
4. Restart services, test.

Rollback is backup-based, not code-based: every file the script touches is copied to a timestamped directory first; restoring means copying those back with services stopped, not running some inverse migration. There is no `down()` method anywhere in this design, deliberately — see the dbutils README's "Undoing it" section.

## The bug this model exposes (round 14, dbutils#52 blocking #1)

Step 0 needs to decide, per instance, "is this one of the pre-existing instances that needs a UTC boundary recorded, or is it a newinst-created instance where every row is already UTC by construction?" The code answers this by reading the instance's own VERSION file and treating "already at 4.3.0" as proof of "created fresh by newinst, under 4.3.0 code." That reasoning is actually correct for a newinst-created instance — VERSION really does prove freshness there, since newinst can only ever create an instance at whatever version its own dbinst checkout is. It's wrong for the *other* kind of instance in case 2: step 2 of the procedure above pulls **every existing instance's own dbinst checkout** to 4.3.0 too, as part of the mandated upgrade sequence — so a genuinely pre-existing 4.2.0 instance also reads VERSION 4.3.0 by the time step 0 runs, identically to a newinst-created one, even though nothing about its data has changed.

The general lesson, not just the specific fix: **don't infer "was this here before the transition" from a signal the transition procedure itself overwrites for every instance, new and old alike.** The boundary table already exists for exactly this reason (an explicit, persistent, per-instance record) — step 0 needs to decide newness from something that survives the pull, such as whether the instance already has any `people_audit` rows at all, not from VERSION.

## What the ansible side needs to do differently

There are two separate ansible codebases, and both currently matter:

- **us3lims-roles** — the existing production playbook set. Actually runs real hosts today, some of which genuinely are on 4.2.0 and need the in-place transition.
- **aucsol_playbooks** — the newer playbook set built for the GMP-validated environment (IQ-qualified installs). Will eventually *replace* us3lims-roles for production too, but that migration hasn't happened and no date is set.

**Scope decision (2026-10-13): keep both working for both fresh installs and 4.2.0→4.3.0 upgrades, until an explicit decision is made about which playbook set owns which use case going forward.** Don't let one lag because the other seems more "current" — `aucsol_playbooks` doesn't integrate `uslims_upgrade.php` at all yet (its `upgrade-playbook.yml` only handles the UltraScan GUI/MPI compute-side git-pull upgrade, not the LIMS web stack or database), so bringing it to parity is new work there, not a port of a fix. Any fix made in one needs an explicit decision about whether it's also needed in the other, rather than assuming the two will naturally converge.

**In us3lims-roles specifically**, `#24` calls `uslims_upgrade.php --apply --yes` on every playbook run, fresh installs included — **correction to this doc's earlier guidance (2026-10-13): that call running on a fresh install is not itself the bug.** `uslims_upgrade.php` is dual-purpose: besides the one-time 4.2.0→4.3.0 migrations, its later steps (breaker/ssh-control/elog directories, the Report-Only CSP policy, the submission sizing-gate verification) are idempotent host *provisioning* that a fresh install needs exactly as much as an upgrade does — the task's own comment says so directly ("a fresh build converges through the exact same logic an existing host's upgrade does"). Skipping the call entirely on a fresh install, as this doc previously said to do, would have skipped that provisioning too. Fixed instead (round 14):

- **Ordering, not case-detection, was the real bug.** The call was interleaved inside `config-lims-lims`, which ran *after* `config-lims-us3-user` had already started `us3-listen` and written the LIMS cron entries — so step 1's idle check failed on every run, fresh or upgraded, because the same play had already made the host not-idle before the call ever ran. Fixed by extracting the service/cron-starting tasks into their own role (`start-lims-services`) and moving it to the very end of the play, after every role that calls `uslims_upgrade.php` (`config-lims-lims`, `install-demo-dbinst`). The host now stays idle through both calls regardless of which case applies — no case-detection needed for this part at all.
- **A missing script (an old dbutils checkout) needs a graceful skip, not a case-detection skip.** A host pinned to a pre-4.3.0 `utils_branch` (deliberately, for compatibility testing, or a genuine 4.2.0 host) doesn't have `uslims_upgrade.php` yet — that must report a clear note and let the play continue, not fail outright on "Could not open input file." This is a existence check (`stat`), not a fresh-vs-upgrade distinction.
- **Settings the upgrade script now owns must not be re-templated over on every run**, fresh or not — this part of the original guidance holds. `config-lims-mpi-runtime`'s own `global_config.php`-writing task was re-asserting `ppbj`/`env_script_lines` unconditionally on every run, including re-runs on an already-upgraded host where `uslims_upgrade.php` step 3 is now the one computing and owning those same settings. Fixed by gating that one task (not the whole role) to a genuinely fresh install only, matching the "one owner per setting" rule `global_config.php`'s own copy task already follows.

  **That same copy task had the matching bug the other direction (round 15):** `config-lims-lims`'s own `global_config.php`-template copy was gated on the *upgrade script's* banner being absent, not on whether the file already existed — correct for an upgraded host (the banner proves it), wrong for a fresh-built host that has never been upgraded at all, since that host never gets the banner either. Every later re-run on it still saw no banner and copied the pristine template straight back over `config-lims-mpi-runtime`'s own detected `ppbj`/`env_script_lines` values, observed going 16 (detected) → 8 (template) → 16 (re-detected) across successive runs. Fixed by gating the copy on the *same* `global_config_existed_already` fact the MPI task already uses, instead of a banner grep: the real question was always "did this run just create the file," and the file's own pre-existence answers it directly, for either owner, without needing to know which one wrote to it.

**Correction (2026-10-14, round 15): the ordering fix above only solved idle-at-start-of-first-run; re-runs on a live host still fail.** Moving `start-lims-services` to the end of the play guarantees the host is idle the *first* time `config-lims-lims`/`install-demo-dbinst` call `uslims_upgrade.php --apply` in a given play — but that same end-of-play step is what puts the host *into* service, and it stays in service once the play ends. The *next* playbook run then hits those same `--apply` calls while the host is still in service from the previous run's `start-lims-services`, before this run's own `start-lims-services` has had a chance to stop anything — so it refuses "not idle" every time, on any host already converged. Ordering within one play was never going to fix this: nothing in that play *tears down* service state between runs, by design (the play is meant to converge a running host, not to bounce it every time).

**Fixed (2026-10-14, round 15):** each of the two call sites now idles itself immediately beforehand, independently, rather than assuming either a prior run or the other call site left the host idle for it:
- `php services.php stop` (the documented graceful shutdown, not `systemctl stop us3-listen` — every host this role builds is already on listen-config v2) if `systemctl is-active us3-listen` says it's running.
- The crontab needs more care than a stop/restart, because `uslims_upgrade.php`'s idle check also refuses on any *uncommented* line matching its own LIMS-job pattern, and `start-lims-services`/`config-lims-backup`/`config-aucsol-backup` all write exactly such lines, active, on every prior run. Commenting them out and uncommenting them back afterward by pattern would collide with `cron-tasks.yml`'s own "deliberately disabled" detection — a line this step left commented would be indistinguishable from one an operator disabled on purpose, so a later run would never re-enable it. Fixed instead by snapshotting `/etc/crontab` whole and restoring it verbatim afterward (`ansible.builtin.copy` of the file, not a regex-based uncomment), wrapped in `block`/`always` so a genuine failure (not the tolerated "still not idle" case) still restores it before the play stops.
- A refusal that still says "the host is not idle" *after* this step means something outside the play's control is using it (a manually-started daemon, a job genuinely in flight) — `failed_when` tolerates that one specific message and the play continues with a note, rather than failing outright; every other non-zero exit still fails the play normally. That satisfies "never run the upgrade on a host that isn't idle" without also requiring "the play must abort if it can't."

**Correction (2026-10-29, round 16): the idle step left the daemons stopped on every re-run.** `php services.php stop` stops the daemons but not the unit: `us3-listen` is `Type=oneshot` with `RemainAfterExit=yes`, so systemd still reported it active and `start-lims-services`' `state: started` never started it again. All three call sites (the playbook preflight, `config-lims-lims`, `install-demo-dbinst`) now share `start-lims-services/tasks/idle.yml` and `resume.yml`:
- A busy host (Slurm jobs, LIMS analysis jobs, or a state that cannot be read) is not stopped, and the `uslims_upgrade.php` call is skipped with a note.
- Otherwise the current unit is installed and systemd reloaded first, so the stop runs under `KillMode=process` even on a host still carrying an older unit (whose default kill mode would take every job monitor down), then `us3-listen` is stopped through systemd. Its `ExecStop` is the same graceful `services.php stop`, and the unit ends inactive.
- `resume.yml` starts it again in each call's `always` block, so the daemons are down only for the call itself and a failed call does not leave them down. `install-demo-dbinst` therefore idles again rather than relying on `config-lims-lims` having left the host idle.

**In aucsol_playbooks**, there is currently no upgrade invocation to fix — it needs to be added, following the same fresh-vs-upgrade detection principle from the start, rather than inheriting us3lims-roles' blurred version and then having to un-blur it a second time.

**aucsol_playbooks' dev/test/val environment variants (`aucsol_playbooks`, `-val`, `-4.2.0`) are an intentional, ongoing construct and stay.** This isn't something to collapse into a single environment while doing this work — any install/upgrade logic added here needs to work across whichever of those variants it's used in, the same way `gmp_enabled`/SELinux-enforcing gating already varies per environment today. **us3lims-roles should not gain this** — it stays a single-environment playbook set; the dev/test/val construct is specific to aucsol_playbooks and isn't something to port backward.

## The release gate and 4.2.0-pinned hosts (round 15, us3lims-roles#24 blocking)

**Fixed:** `site_release` was off by default (the playbook never set it, so `release-gate` never ran against the playbook's own defaults, only a site that happened to define it independently), covered six of the eight `*_branch` pins (`dbinst_branch`/`us3_branch` were never checked against it at all), and only caught a mismatch once the first role that includes `release-gate` actually ran (after four earlier roles had already touched the host). Fixed by making `site_release` the single source of truth all eight pins now derive from by default, and adding a `pre_tasks` check of all eight against it, before any role runs at all — needs no filesystem access, so it costs nothing to run first.

**Correction (2026-10-29, round 16): one variable cannot be both the ref and the VERSION.** `release-gate` compared `site_release` with each checkout's ref (`release-2026-Q3`, `v4.2.0`) and with its VERSION file (`4.2.0`), so any real ref name failed one check or the other. The release is now two required values: `site_release` is the ref every `*_branch` pulls, and `site_release_version` is the VERSION that ref carries, compared with each checkout's VERSION file. `site_release_version` is required whenever `site_release` is set; `pre_tasks` and `release-gate` both refuse to run without it (an optional version would fall back to a ref-only gate). Logic that depends on the release (the pre-4.3.0 Airavata bridge) keys on `site_release_version`, never on parsing the ref.

**Fixed (2026-10-29, round 16): a run on a 4.2.0 host changes nothing, and a fresh 4.2.0 install works.** Measured, not inferred: a VM built by main's roles at `release-2026-Q3` (VERSION 4.2.0), a full before/after capture (file checksums and owners, database users, grants, schema and `newus3.people`, service start times, crontabs, checkout heads), then a run of this playbook with `site_release_version: 4.2.0`, compared against a re-run of main itself on the same snapshot (`scripts/test-roles-420-rerun.sh` in uslims_stack).
- `pre_tasks` sets `lims_pre_430` from `site_release_version`. Every 4.3.0-specific change is skipped for it: the `newus3.people.account_enabled` ALTER, the gfac CREATE/ALTER/INDEX grant, `config-lims-dbinst-base`, `config-lims-mpi-runtime`, the php-fpm KillMode drop-in and log permissions, the `$common_dir` lines in the webinfo and newinst configs, the `/common` aliases in the SSL vhost, the newer `us3-listen` unit (a 4.2.0 host keeps main's), and the admin-provisioning marker on an existing host. A pre-4.3.0 site still gets the Airavata bridge and `airavata_branch` in dbutils' `db_config.php`.
- Re-runs that failed or changed things on main as well, fixed here because the zero-change requirement cannot hold without them: grants to a host name (ignored under `skip-name-resolve`, error 1141 after any MariaDB restart) are made only for an IP `server_name`; the MariaDB settings block, `safe.directory` entries and the msttcore RPM are added once; the demo import runs only when `uslims3_Demo` does not exist; MariaDB, slurmd and postfix restart only when their configuration changed. A fresh install also needed the EPEL signing key imported first and the Slurm RPM path to follow the host architecture.
- Remaining, also done by main's own re-run: the first re-run of a main-built host normalizes `uslims3_Demo`'s group from `us3` to `apache` (`config-lims-lims`' recursive ownership task; main's demo role creates it with the other group). A second run changes nothing.

**Fixed (2026-10-29, round 16): a mid-upgrade host with open `[input]` items is refused before anything changes.** `uslims_upgrade.php --check` exited 0 when the open work was `[todo]`/`[input]`, so the preflight passed and the play's `--apply --yes` made 11 changes before stopping at two `[input]`s. Now `--apply` runs the check pass itself first and refuses, before any change, while an `[input]` it cannot ask for is open; `--check` exits 3 for an open `[input]` and prints a `SUMMARY` line; and the preflight (`release-gate/tasks/upgrade-state.yml`) refuses exit 3 with the open items named, before any checkout moves.

**Fixed:** `listen-config.php` had the identical "wrong gating signal" bug `global_config.php`'s own copy task did (see above) — gated on `$listen_config_version`'s presence, a 4.3.0-only marker that a 4.2.0-pinned site's own gridctl checkout never writes, so this task re-templated the file from that older template on *every* run, not just the first, silently dropping `$host_name` (the older template has no such placeholder) along the way. Fixed the same way: gated on the file's own pre-existence instead.

**Not yet investigated, and flagged rather than guessed at:** the review's fuller 4.2.0 scenario also names a fresh 4.2.0 install having no working Airavata/GFAC submission bridge (web submission 500; manage/submit/esign down), an existing 4.2.0 host's run touching 5 files and adding 6 beyond `listen-config.php`, and `config-lims-mpi-runtime`'s detection/asserts running on 4.2.0 hosts where they may not apply. None of these have a concrete, individually-reproducible bug description the way the two fixes above did, and confirming or fixing them needs either the original ticket's exact spec for what a 4.2.0-pinned run is supposed to do, or an actual 4.2.0 host to test against (not available in this environment) — invented fixes here would be guesses dressed up as fixes, which is worse than leaving the gap open and named.

## What this means for future releases (past 4.3.0)

The pattern repeats for the next shape change: add migrations to the registry, keep installs and upgrades on separate detection logic, never let a fresh install touch the migration machinery, and never infer "was this here before" from a value the upgrade procedure itself changes along the way. If a future round of review finds the same class of bug again, it means this doc wasn't followed, not that the bug is new.
